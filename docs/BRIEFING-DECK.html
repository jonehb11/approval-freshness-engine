Engineering governance · Briefing

Approvals should expire when the code changes — not when the clock ticks.

A fail-closed replacement for GitHub's "dismiss stale approvals on any push," deployed and tested against real pull requests.

Approval Freshness Engine · deterministic-only deployment · 2026-08-01
The recommendation

Adopt it — but only after a measurement that gives us permission to walk away.

GitHub throws away a human approval whenever any commit lands, even a formatter run or a branch update that changed nothing. That costs reviewer attention and buys no safety. This engine replaces the staleness test — not the review requirement.

What it does

Keeps an approval alive when the change since approval is provably nothing. Demands fresh human review whenever it isn't.

What it cannot do

Approve, merge, or push. Its entire vocabulary is dismiss a review, set one check, or do nothing.

What it costs to be wrong

Every failure lands on a blocked merge — exactly what GitHub does today. Proven, not asserted.

Supporting argument 1 of 3

Today we pay a re-review tax that verifies nothing.

A reviewer who has already read a change is asked to read it again because a typo was fixed or an unrelated PR merged first. The second look is ceremony: it audits well and verifies little.

Supporting argument 3 of 3

It cannot fail open, because it is not the gate.

The merge gate is GitHub's own ruleset, evaluated natively on every merge attempt. The engine's only power is to try to make one boolean true. If the engine dies, that boolean stays false — and false means blocked.

No dead-man switch

Nothing counts down. Nothing reverts. No runtime component can edit a ruleset — that credential does not exist anywhere in the system.

No frozen merges

A fresh human approval on the current commit always clears the block — the same action GitHub asks for today.

Proven, not claimed

We killed the engine for five minutes and pushed to an approved PR. It stayed blocked. No timer rescued it.

How it works · the whole design in four lines

The merge equation.

merge allowed ⇔ approving reviews ≥ 1 AND check approval-freshness/evaluated == success on the CURRENT head commit from the engine's GitHub App only

Checks are matched per commit, so every new push starts blocked by construction. The App identity is pinned in the ruleset: a check with the same name from any other identity is rejected by GitHub as "not set by the expected GitHub App."

Only two things can ever turn that check green: the engine proving the change is null, or a real human approving the current commit. There is no third path.

How it works · the decision

Three rungs. The machine judgment is last, optional, and outranked.

Stage 0

Hard rules — plain code, no AI

Privileged paths, force-push, commits by anyone but the author, size caps, injection canaries. Glob matching and integer comparisons. It can only block.

BLOCK ONLY
Stage 1

Structural diff — difftastic, no AI

Parses both versions into syntax trees and compares the trees. Formatting, indentation and blank lines vanish; real code changes do not. It can only preserve.

PRESERVE ONLY
Stage 2

Classifier — advisory, gated, switchable

One structured verdict, no agent loop. It cannot preserve alone: the change must also be small, touch nothing sensitive, and add no dependency. Now proven: 0 false preserves on the golden set, and every deterministic gate was shown to overrule it.

How it works · for the developer

What keeps your approval, and what doesn't.

Approval survives

  • Formatter runs, re-indentation, line reflow
  • Blank lines, trailing commas
  • Docs and *.md only
  • "Update branch" when your files didn't change

Human must look again

  • Any real code change
  • Workflows, Terraform, prod config, manifests
  • A commit from someone who isn't the author
  • Force-pushes, oversized diffs
  • Comment edits — comments are syntax, not whitespace

That last line is a correction we made because of live testing. We had documented comment typo fixes as preserved. We ran it: difftastic treats comments as syntax-tree nodes, so they are a real change. The claim was wrong, and the docs now say so.

Evidence · the part most decks leave out

Live testing found ten defects that the unit suite did not. Three let real attacks through.

The headline feature was dead

Stage 1 asked difftastic for JSON output. That version refuses it and exits with an error code the engine read as "unsupported language" — for every file, in every language. Approval preservation could never fire, while every health signal stayed green.

Three real bypasses

A change kept its approval and became mergeable in three cases: an added dependency (const x = require(…) missed the gate), an executable script under docs/, and a CI workflow file one directory deep. All blocked now.

One root cause

Every one was a gate answering "safe" because it had nothing to look at — an empty list, an empty patch, a truncated diff, a path pattern anchored one directory too tightly. Absence of evidence was reading as evidence of absence.

Why this matters more than the passes. All ten were invisible to a test suite that mocked the outside world. That is the argument for the shadow phases: run it against real traffic before trusting it. All ten are fixed, each with a regression test, each re-verified against a live pull request.

Decision · what we cannot claim

What is not yet proven.

  • The AI layer is proven but young. Zero false preserves on a ten-case golden set, and the deterministic gates were shown to overrule it live — but ten cases is a starting point, not a track record.
  • The offline-recovery path is now proven — with the engine fully dead, a human approval flipped the check green, written by GitHub Actions but attributed to the engine's own App identity. The cost is real and stated: it needs a second copy of the App key in Actions secrets, and an org may decline it.
  • Scale is untested. A handful of concurrent PRs, not production load.
  • Ruleset deletion is a genuine fail-open and drift monitoring is documented but not built.
  • Lost webhooks are not replayed. Safe, but a human must push again.

If we told you this was production-complete, you should not believe the rest of the deck either.

Appendix

Speaker script.

Open · the recommendation first

"I'm going to give you the answer up front, then the reasons, then the evidence — including the parts that didn't work.

The recommendation: we should adopt this, but only after a measurement that gives us permission to walk away. Here's the problem it solves. Today, GitHub throws away a human approval whenever any commit lands on the pull request. Any commit. If you fix a typo, run the formatter, or click 'Update branch' because someone else's work merged first — the approval is gone and somebody has to look again at code that did not change."

Argument 1 · the tax

"That second look is ceremony. The reviewer already read this change. Nothing about it is different. They click approve again, and we've spent two people's attention to verify nothing. It audits beautifully and it catches nothing.

Pause. I'm not going to put a made-up percentage on that. Phase P0 is a read-only scan of our own history that tells us our real number. If it's small, the honest answer is that we shouldn't deploy this — and I'll say so."

Argument 2 · it's stricter where it counts

"The second thing to understand is that this is not a loosening. Today we apply one blunt rule to every push. This applies a categorical rule to the dangerous surfaces.

Touch a CI workflow, Terraform, production config, IAM, a dependency manifest — a human reviews it, every time, no exceptions, no model involved. Someone else pushes to your branch, or history gets rewritten — same thing. We're moving review attention from ceremony to substance."

Argument 3 · it cannot fail open

"Third, and this is the one the security team will care about: the engine is not the gate. GitHub's own ruleset is the gate. The engine's entire power is to try to make one checkbox true. It cannot approve, cannot merge, cannot push, and cannot edit the rule that governs it — that credential doesn't exist anywhere in the system.

So if the engine crashes, the checkbox stays false, and false means blocked. We tested this: we killed it for five minutes and pushed to an approved PR. It stayed blocked. Nothing rescued it, because nothing is supposed to.

But blocked-forever would be its own outage, so we tested the other half too. With the engine still dead, a reviewer approved the current commit — and the check went green anyway, because a small GitHub Actions workflow can act as the engine's own App identity. Developers self-unblock. On-call fixes the engine at their leisure, never to rescue anybody."

Transition · going technical

"That's the business case. Let me show you the mechanism, because it's four lines and it's worth understanding."

The merge equation

"A merge is allowed if and only if: there's at least one approving review, and a check called approval-freshness/evaluated is green on the current commit, and that check was written by our GitHub App specifically.

Two things matter here. Checks are matched per commit, so every new push starts blocked automatically — we don't have to do anything to block, we have to do something to unblock. And the App identity is pinned, so another workflow writing a check with the same name is rejected by GitHub itself.

Only two things can turn it green: the engine proving the change is nothing, or a human approving the current commit. There is no third path, by design."

The ladder

"The decision has three rungs, and the machine judgment is last, optional, and outranked.

Stage 0 is plain code — glob matching and integer comparisons. Privileged paths, force-pushes, foreign commits, size caps. It can only block, never preserve.

Stage 1 is difftastic, an open-source structural diff. It parses both versions into syntax trees and compares the trees, so formatting disappears and real code changes don't. It can only preserve, never block.

Stage 2 is the classifier. It's advisory: it cannot preserve on its own — the change also has to be small, touch nothing sensitive, and add no dependencies. And in the version we deployed and tested, it's switched off entirely. Everything I'm about to show you is deterministic."

Evidence · what we did

"We didn't just write this — we deployed it and attacked it. Twenty-eight real pull requests, real webhooks, a real gate. Ninety-nine of a hundred and five assertions passed.

Twelve of those were deliberate bypass attempts. We tried hiding a new function inside a formatting-only diff. We rewrote an authorization check to always return true. We tried case-evading the denylist with a capital G in dot-GitHub. We put prompt injection in a comment telling the classifier to mark it low-impact. All twelve were blocked.

We also confirmed the rule binds the repo owner — I couldn't push to main myself."

Evidence · what went wrong (do not skip this)

"Now the part I'd want to hear if I were you. Live testing found three real defects that a hundred and forty-one passing unit tests did not.

The worst one: the headline feature was completely dead. Stage 1 was asking difftastic for JSON output, and that version of difftastic refuses — it exits with an error code that our code read as 'unsupported language.' For every file. In every language. So approval preservation could never happen at all, while every health check stayed green and every test passed.

Let that sit for a second. That's the strongest argument I can make for the shadow phases. You cannot find that class of bug by mocking the outside world. All three are fixed and re-verified against real pull requests."

Limits

"What I can't claim: the AI layer is unexercised — we turned it off. Scale is untested. Deleting the ruleset is a genuine fail-open and the drift monitoring for it is documented but not built. And if a webhook is lost during an outage, nothing replays it — safe, but a human has to push again.

If I told you this was production-complete, you shouldn't believe the rest of the deck."

The ask · close

"So the ask is small and reversible: approve P0. It's a read-only scan of our own history. It writes nothing, touches no gate, and its only possible output is a number.

We agree the threshold before we see that number. If we're below it, we stop, and we'll have spent a week to avoid building the wrong thing. If we're above it, everything after that is a separate decision made with evidence instead of argument.

Questions."
